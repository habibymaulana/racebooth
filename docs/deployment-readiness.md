## Readiness decision

The application has a sound local foundation, but it is **not ready for a real public launch**. The public free-session flow, protected operator routes, gallery capability links, image pipeline, additive migrations, and optional operator-requested Hermes diagnoses are implemented. The R2 adapter and cleanup worker are prepared, but no real R2 bucket or cloud credentials have been provisioned or verified. Production endpoints/secrets, public n8n and Hermes connectivity, domain/HTTPS routing, Neon schema/account setup, and a reviewed initial GitHub commit remain outstanding.

## What is already in place

- Vite serves a static React app. Its Axios client uses relative `/api` requests with credentials, so the production frontend can keep the browser same-origin by proxying `/api` to the API service.
- Express has a PostgreSQL-backed operator session store, CSRF token checks, origin checks, rate limits, Helmet headers, and a production guard that refuses `COOKIE_SECURE=false`. The session cookie is `HttpOnly`, `SameSite=Strict`, and uses the `__Host-` prefix when secure cookies are enabled.
- PostgreSQL TLS verification is supported through `PGSSL=true` and an optional CA file. Schema changes are additive migrations under `database/migrations/`.
- Photos are not served from a public static directory. Gallery QR tokens are scoped, signed, and expiring; the local filesystem remains the development default and production is guarded to use the new private R2 adapter. Gallery TTL is configurable and an opt-in bounded cleanup worker removes expired photo/strip assets.
- Email is dispatched server-side to an n8n webhook with `X-Racebooth-Secret`; the backend records provider confirmation separately from webhook acceptance.
- Hermes is separated from PostgreSQL, photos, and n8n in the local Compose setup. Its local profile uses private key files and its integration is optional and recommendation-only.

## Recommended online architecture

1. **Frontend:** Vercel static Vite build at `https://booth.<domain>`. Add a Vercel rewrite from `/api/:path*` to `https://<persistent-api-host>/api/:path*`, before the SPA fallback. Keep API responses `Cache-Control: no-store`; do not opt the rewrite into CDN caching. Use Vercel environment variables only for public build settings, never credentials. Vercel documents external-origin rewrites and per-environment variables ([rewrites](https://vercel.com/docs/routing/rewrites), [environment variables](https://vercel.com/docs/environment-variables)).
2. **Backend:** persistent Node 24 container with Sharp and the existing Express app. Place it behind HTTPS ingress; allow database, n8n, and Hermes egress only as required. Set the actual trusted proxy count, `NODE_ENV=production`, secure cookies, exact origins, bounded upload limits, and graceful health checks. Do not move the whole API to short-lived frontend functions because sessions, image processing, webhooks, and storage need a persistent service model.
3. **Database:** persistent managed PostgreSQL with TLS verification, private ingress, backups/PITR, migration tracking, and restore drills. Preserve `TOKEN_ENCRYPTION_KEY` during migration so existing encrypted tokens and derived gallery signatures remain verifiable. Use a separately generated production `SESSION_SECRET` and service credentials from a secret manager.
4. **Photos:** private R2 bucket with public access blocked, server-side encryption, and the new backend storage adapter. Keep gallery authorization and downloads on the backend; the adapter does not hand out object URLs. The cleanup timer can remove assets after gallery expiry once explicitly enabled. Never put visitor photos or share tokens in Vercel static assets or n8n execution history.
5. **n8n:** a persistent service with persistent database and user folder. Backend-to-n8n webhook access should use TLS and the existing header secret; keep the editor behind a private access layer. Make the Gmail workflow always available, but retain manual approval for any later workflow changes.
6. **Hermes/Groq:** private backend-to-Hermes service path only; no public gateway, database, or photo-storage access. Keep model diagnosis request-driven, sanitized, and recommendation-only. Rate limits/inference failures must remain non-blocking for photo and email flows.

## n8n migration requirements

The local n8n instance must remain intact as the rollback copy. No export or backup was created during this audit.

1. In a planned backup window, record the exact running image/version and deployment settings. Take a consistent backup of the full `n8n_data` volume; because the current instance appears SQLite-backed, stop it only for the duration needed to make a consistent volume snapshot. Preserve the volume contents and encryption key. n8n's complete backup includes the `.n8n` folder and, when PostgreSQL is used, its external database too ([n8n backup/restore](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/backup-and-restore/)).
2. Separately export the current Gmail workflow and credential entities with n8n's CLI `--backup` exports into a private, encrypted backup location. The CLI exports do not include user accounts, execution history, instance settings, or the encryption key. Do **not** use `--decrypted`; that produces plaintext credentials. Restore encrypted credentials with the same key or reauthorize them securely in the target ([CLI backup details](https://docs.n8n.io/deploy/host-n8n/configure-n8n/use-the-command-line/)).
3. Provision the target encryption key through the hosting secret manager before importing credentials. The key is required to decrypt existing credentials; losing it makes those credentials unrecoverable ([n8n encryption-key guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key/)). Do not paste it into Git, tickets, or this report.
4. Update the Google OAuth app's authorized redirect URI to the target n8n callback URL shown by the credential setup. Preserve OAuth client credentials securely; after import, test or reauthorize the Gmail credential from the protected editor. A workflow JSON alone does not migrate OAuth access/refresh tokens.
5. Give n8n a public HTTPS webhook base URL while keeping the editor private. Set `N8N_WEBHOOK_URL` and the correct `N8N_PROXY_HOPS`; configure the final reverse proxy to forward `X-Forwarded-For`, `X-Forwarded-Host`, and `X-Forwarded-Proto`, as n8n requires behind a proxy ([webhook proxy guidance](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-webhook-urls-with-reverse-proxy/)). Keep production webhook URLs separate from the local `n8n:5678` endpoint.
6. Recreate the Gmail webhook path and require `X-Racebooth-Secret` with a new random secret provisioned independently in the backend and n8n. Validate allowed URL host, expiry, recipient, and `delivery_id`; return the provider message/thread IDs and `SENT` acknowledgement expected by the backend. Prune/redact n8n executions so visitor email addresses and gallery bearer links are not retained unnecessarily.
7. Test the migrated workflow in a non-production/staging setup first. Keep the local n8n container, volume, credentials, and old webhook unchanged. Do not point production traffic at the new workflow until an explicitly authorized acceptance test succeeds.
